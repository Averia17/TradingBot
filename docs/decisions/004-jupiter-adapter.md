# ADR-004 — Jupiter Adapter и наблюдение за кошельком

**Статус:** принято 22.11.2026.

Jupiter Adapter — отдельная Go-команда внутри модуля `services/venue-quotes`.
Она использует существующий клиент Jupiter и сохраняет HTTP-контракт котировок.
Для текущей цены в USD используется Jupiter Price v3. Обе стороны обмена
готовятся через Swap v2 `/order` с адресом одного настроенного кошелька,
нативным USDC Solana и точным входным количеством. Для подготовительного
запроса необходимы целочисленный минимум выхода и допустимый slippage в bps.
[Swap v2](https://developers.jup.ag/docs/api-reference/swap/order) ·
[Price v3](https://developers.jup.ag/docs/api-reference/price) ·
[Mint USDC](https://developers.circle.com/stablecoins/usdc-contract-addresses)

Ответ подготовки содержит кандидат транзакции Jupiter, срок по высоте блока
и request ID. Подготовка и отправка включаются независимо. Перед отправкой
адаптер проверяет подпись торгового кошелька, утверждённый хеш политики,
подпись независимого проверяющего и действительность blockhash. Сам
проверяющий подтверждает разрешённый маршрут, резерв и смысл инструкций.
Актуальное решение по допуску записано в [основном плане](../planning/plan.md).

Фактические активы кошелька учитывает Solana. Тот же адаптер читает lamports,
SPL Token и Token-2022 с commitment `finalized` через настроенный Solana RPC.
Публичный Jupiter Portfolio API закрыт. Снимок сохраняет slot каждого
RPC-ответа и содержит наблюдаемые остатки отдельных token accounts. В live-протоколе
Go ledger будет вести резервы и рассчитывать доступный для торговли остаток.
[Jupiter changelog](https://developers.jup.ag/changelog/2026-10) ·
[Solana getBalance](https://solana.com/docs/rpc/http/getbalance) ·
[Solana getTokenAccountsByOwner](https://solana.com/docs/rpc/http/gettokenaccountsbyowner)

Полный снимок живёт пять секунд в памяти процесса. Принудительное чтение
сбрасывает кэш, а при отказе RPC запрос возвращает ошибку. При обновлении
проверяется genesis hash Solana mainnet. Адаптер сбрасывает кэш до и после
вызова Jupiter Execute, а также когда чтение квитанции подтверждает
финализацию в Solana. До сверки Go ledger удерживает резерв. Для live-проверок
нужен контроль слота относительно исполнения и независимое подтверждение.

## Протокол отправки

- Перед отправкой verifier получает от Go ledger действующий резерв,
  полностью проверяет транзакцию согласно политике владельца и подтверждает
  подписанный payload. У адаптера есть публичный ключ verifier. Это
  отдельный ключ Ed25519 от ключа торгового кошелька.
- Поле `approval` содержит стандартный Base64 от компактного JSON
  `ExecutionApproval`. Порядок полей совпадает с Go-структурой
  [Approval](../services/venue-quotes/internal/jupiter_execution/approval.go).
  `approval_signature` — стандартный Base64 подписи Ed25519 над UTF-8
  префиксом `TradingBot Jupiter Swap Approval v1\n` и байтами этого JSON.
  Хеш транзакции вычисляется от декодированных байтов
  `signed_transaction_base64` и передаётся в lowercase hex. Подписанный
  документ связывает intent, резерв, кошелёк, активную версию политики,
  request ID Jupiter, срок и точные байты транзакции.
- PostgreSQL атомарно фиксирует попытку до сетевого вызова. Повтор того же
  одобрения возвращает квитанцию. Повтор intent с другим одобрением, а также
  повтор резерва, подписи или Jupiter request ID в другом intent возвращает
  конфликт. Таймаут и авария между записью и отправкой сохраняют
  `provider_status=unknown` и подпись для дальнейшей сверки.
- `provider_status` отражает только ответ Jupiter. Для наблюдения
  финализации адаптер сверяет два метода одного Solana RPC. Если
  финализированных метаданных нет, состояние остаётся нефинальным.
  `chain_status: null` в квитанции означает, что наблюдение отсутствует.
  Go ledger должен отдельно сверить изменение активов и фактические fills.
  [Jupiter Execute](https://developers.jup.ag/docs/api-reference/swap/execute) ·
  [Solana getSignatureStatuses](https://solana.com/docs/rpc/http/getsignaturestatuses) ·
  [Solana getTransaction](https://solana.com/docs/rpc/http/gettransaction)

Критерии приёмки среза:

- Котировка сохраняет существующий wire format. Цена сохраняет точное десятичное
  значение и время получения. Ошибка источника не превращается в нулевую цену.
- BUY и SELL корректно разворачивают пару. Подготовка отвергает расхождение
  mint или суммы, слишком низкий заявленный провайдером минимум выхода,
  уже прошедшее время `expireAt`, неподдерживаемый router, спонсируемую оплату
  и ошибки Jupiter.
- Баланс сохраняет точные raw amounts, включая нули, и слоты всех RPC-ответов.
  Проверки покрывают истечение TTL, принудительное чтение, отказ источника
  и конкуренцию. Тесты используют локальные ответы, без реальных операций.

Сквозной сценарий использует существующий paper ledger для резерва и расчёта,
журнал адаптера для попытки отправки и тестовый транспорт для Jupiter и
Solana. Отдельный тестовый signer восстанавливает ожидаемое Memo v0 по
разрешённому сценарию и сравнивает полные байты до подписания. Проверка
инструкций реального Metis и подтверждение реального исполнения относятся
к live gate. [Запуск прогона](../architecture.md#сквозной-офлайн-прогон-jupiter)

Периодический paper-цикл подключает тот же тестовый контур через локальный
callback после штатных проверок и атомарного резерва. Режим закреплён
в котировке как `jupiter_fixture`. При отсутствии соответствующего режима
диспетчера заявку нельзя завершить через обычную симуляцию. Неопределённый
ответ оставляет заявку в работе. При повторном чтении уже записанного
исполнения диспетчер восстанавливает квитанцию из ledger.
[Периодический прогон](../architecture.md#jupiter-в-периодическом-paper-цикле)
