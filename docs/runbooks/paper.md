# Восстановление локального paper-контура

Запускайте проверку из корня репозитория. Нужны Python 3.11 или новее,
установленный Go из `services/control/go.mod`, закэшированные модули Go
и образ PostgreSQL 17 с digest из [Compose](../../deploy/research/compose.yaml).

```powershell
python deploy/research/restore_smoke.py
```

Проверка собирает Go control и использует две отдельные временные базы с портами
на `127.0.0.1`. Go использует локальный toolchain и кэш модулей, Docker использует
локальный образ. Скрипт создаёт виртуальный счёт с одним исполненным BUY и одним
`UNKNOWN`, завершённый research job и активную попытку второго задания.
Активная попытка получает одно разрешение на вызов модели. Оно полностью
исчерпывает суточный лимит проверки. Все результаты синтетические, внешние
вызовы не выполняются.

После остановки исходного Control скрипт создаёт `pg_dump -Fc`, удаляет исходный
контейнер и восстанавливает архив в пустой базе командой `pg_restore` в одной
транзакции. Восстановленный Control должен вернуть прежний баланс, историю,
резерв, квитанции и исчерпанный суточный лимит. После истечения исходного
lease база отклоняет новый вызов. Второе задание завершается офлайн-результатом
без вызова. Контроль повторов проверяет, что появляются ровно одна новая
запись исполнения, одно событие paper ledger, одно ожидающее уведомление,
один research result и одно событие completion outbox. Скрипт выводит SHA-256, размер архива и счётчики до и после
возобновления, затем удаляет свои контейнеры и временный архив.

## Восстановление журнала планировщика

```powershell
docker compose -f deploy/research/compose.yaml --profile paper-entry build control paper-entry
python deploy/research/restore_smoke.py --entry-journal
```

Проверка использует готовые образы Control и `paper-entry`. Если образы
собраны с другими тегами, укажите `TRADINGBOT_CONTROL_IMAGE` и
`TRADINGBOT_PAPER_ENTRY_IMAGE`. Первый запуск принимает одно задание и
сохраняет запрос второго в журнале перед имитацией сбоя. Скрипт останавливает
пишущие процессы и восстанавливает PostgreSQL и отдельный том журнала
в новом Compose-проекте. После восстановления первое задание сверяется
даже после дедлайна, второе ставится в очередь один раз. Повторная проверка
сравнивает байты журнала и идентификаторы событий с первым успешным запуском.

Для журнала пересмотров запустите отдельную проверку с теми же образами.

```powershell
python deploy/research/restore_smoke.py --review-journal
```

Скрипт создаёт тестовую позицию и обрывает процесс между записью задания
в PostgreSQL и подтверждением в SQLite. Затем он восстанавливает обе копии
в отдельном Compose-проекте и повторяет исходное окно пересмотра.

У `paper-review-cycles` отдельный SQLite-журнал `reviews.sqlite3`. Статус
`pending_go` означает, что запрос уже записан, а подтверждение PostgreSQL
ещё требуется сверить. После рестарта используйте тот же том, план и архивы.
`already_scheduled` возвращает ID ранее принятого задания для следующего
окна того же триггера. `not_due` и `not_open` закрывают конкретное окно.
`missed` означает, что срок окна истёк до постановки. `refused` указывает
на проблему со входами окна, при этом процесс продолжает проверять остальные
окна. План привязан к журналу. Для новой версии плана используйте другой журнал.

## Перенос постоянного локального paper-счёта

1. Остановите планировщики `paper-entry`, `paper-review` и `paper-review-cycles`,
   воркеры и диспетчеры бумажного счёта. Проверьте `/readyz` и зафиксируйте
   версию счёта и незавершённые заявки по API учёта. Затем остановите Control.
2. Снимите custom-format архив базы торгового проекта через `pg_dump -Fc` и
   скопируйте его за пределы исходного контейнера и тома. Сохраните SHA-256
   архива, версию Postgres и идентификаторы версий Control и воркера.
   Сохраните содержимое томов `paper-entry-journal` и `paper-review-journal`,
   неизменённые архив и конфиг владельца, а также опубликованные котировки.
3. Подготовьте пустую изолированную базу с нужной ролью. Примените `pg_restore
   --single-transaction --exit-on-error` к этой базе. В тесте роль назначения
   владеет всеми объектами, поэтому используется `--no-owner --no-privileges`.
   При других ролях проверьте права Control на целевой базе до переключения.
4. Запустите Control с новой базой и проверьте `/readyz`. До возобновления
   планировщика и воркера сравните версии и резервы счёта, последние результаты
   и события. Проверьте `UNKNOWN` по источнику paper-наблюдений. При наличии
   повторной доставки используйте исходные ID и исходное содержимое заявки,
   события или завершения задания. Восстановите журналы и прежние файлы
   до запуска планировщиков, передайте прежние хеши планов.
   Активные lease продолжают действовать до своих сохранённых дедлайнов.

Для задания, которое было остановлено во время анализа, снимите
`research-usage-export --job <UUID>` до копирования и после восстановления.
Сверьте хеши выгрузок до возобновления воркеров. Исходное разрешение без
ответа по-прежнему должно занимать слот. [Команда выгрузки](../../README.md).

Локальная проверка покрывает логический архив на одной версии PostgreSQL и
синтетические входы. Периодичность копирования, хранение архивов, целевые RPO/RTO
и восстановление внешнего архива данных измеряются отдельно.

## Проверка состояния после запуска Control

Укажите параметры чтения целевой PostgreSQL в `TRADINGBOT_DATABASE_URL` и
подставьте UUID счёта и задания. Роли нужны доступ к схеме и `SELECT` на таблицы
журнала и учёта. С ключом `--job` добавляются таблицы research jobs, результатов
и разрешений.

```powershell
go -C services/control run ./cmd/paper-check --account $paperAccountId --job $researchJobId
```

Проверка использует один read-only снимок PostgreSQL и возвращает JSON с
версиями счёта и воспроизведения журнала. Она сверяет точный остаток cash и
объёмы позиций с FIFO-проекцией, выявляет просроченные заявки и `UNKNOWN`,
который длится дольше `--unknown-after` (по умолчанию `5m`). Если передан
`--job`, она также проверяет остаток общего лимита, квитанции и расход по
завершённой попытке. Выданное разрешение без подтверждённого результата
помечается как неподтверждённый расход. Вывод содержит подтверждённое число
вызовов и число вызовов с неполной токеновой телеметрией.

Для автоматизации соберите команду через `go build`. Код выхода `0` означает
`ok`, `1` сопровождает результат `attention` со списком проблем и ID,
`2` означает `unavailable` или ошибку конфигурации. Команда оставляет счёт и
резервы под управлением Control. При `UNKNOWN` сверяйте исход наблюдения
по исходному `order_id`. При расхождении учёта сначала проверьте журнал
по указанной `account_version`. При сомнительном бюджете используйте записи
выданных разрешений до возобновления research job.

Ключ `--pipeline` добавляет состояния планирования, исследования и
применения выбранного счёта, а также очередь передачи исполнений.
Понадобится право `SELECT` на `research_paper_dispatch`, `research_jobs`,
`research_job_attempts`, `research_job_results`, `paper_applications`,
`paper_orders` и `paper_fill_outbox`.

```powershell
go -C services/control run ./cmd/paper-check --account $paperAccountId --pipeline --stall-after 2m
```

Срез содержит до 100 незавершённых dispatch. При превышении лимита
`paper_pipeline_truncated` помечает неполный отчёт. Ключ `--job` показывает
также завершённый dispatch выбранного задания, если он привязан к счёту.
Поле `selected_job_registered` подтверждает наличие этой привязки.

| Код | Что видно в PostgreSQL |
| --- | --- |
| `research_queue_stalled` | Задание остаётся в очереди дольше порога. Сверьте готовность и опрос Python worker. |
| `research_lease_expired` | Истёк срок текущей аренды. Сравните номер попытки и остаток бюджета перед возобновлением. |
| `paper_dispatch_application_stalled` | Исследование завершено, ещё нет записи применения. Сверьте диспетчер, сохранённую политику и входную котировку по ID задания. |
| `paper_dispatch_recovery_stalled` | Резерв существует без квитанции применения. Проверьте исходную заявку и сохранённую котировку перед повтором. |
| `paper_dispatch_ack_stalled` | Квитанция записана, dispatch ещё не подтверждён. Порог отсчитывается от создания записи применения. |
| `paper_dispatch_research_failed` / `paper_dispatch_research_expired` | Диспетчер ещё не подтвердил завершение неуспешного исследования. |
| `paper_dispatch_inconsistent` | Связанные строки, идентификаторы или хеши не сходятся. Проверьте исходные записи по ID из отчёта. |
| `paper_fill_relay_stalled` | Самое старое исполнение ещё не передано из журнала. В отчёте есть его ID, время и число ожидающих исполнений. |

Порог по умолчанию составляет 5 минут. Время проверки берётся из
PostgreSQL. Наличие локальной котировки, доступность Kafka и доставка
уведомления проверяются по их собственным данным. Поле `fill_relay`
описывает только передачу из PostgreSQL outbox.
[Схема отчёта](../../contracts/paper-check.schema.json) · [Пример отчёта](../../contracts/valid-paper-check.json).

## Сверка зависшей виртуальной заявки

Сохраните локальное наблюдение симулятора по исходным `account_id`,
`order_id` и `quote_id`. Время наблюдения и время получения фиксируются
отдельно. Для частичного или полного исполнения укажите raw units,
фактические gross и fee. Для отмены укажите только исход наблюдения.
[Контракт](../../contracts/paper-reconciliation.schema.json) · [Пример](../../contracts/valid-paper-reconciliation.json).

```powershell
go -C services/control run ./cmd/paper-apply reconcile --observation $observationPath --sha256 $observationSha256
```

Команда работает с виртуальными заявками в статусе `UNKNOWN` или
`partially_filled`. До записи наблюдения резерв сохраняется. Исполнение
учитывает только подтверждённые единицы, отмена освобождает оставшийся
резерв. Идентификатор наблюдения становится ID события, SHA-256 сохраняется
в журнале. Для повторной доставки используйте исходный файл и хеш. При
выдаче нового статуса смотрите текущую запись ордера. Первоначальная
квитанция `paper-apply follow` сохраняет результат своего запуска.

## Отказы проверки риска до резервирования

```powershell
go -C services/control run ./cmd/paper-apply refusals --account $paperAccountId --job $jobId
```

При проверке привязанных исследования и котировки `paper-apply apply`
и `paper-apply follow` сохраняют нарушения лимита риска, пока версия
счёта и сроки применения действуют. Запись связывает код причины и время
первого наблюдения PostgreSQL с решением, хешами запроса и котировки.
`candidate_order_id` вычисляется для проверенной заявки до её создания.
При заданном `max_execution_cost_bps` код `maximum_execution_cost`
означает превышение лимита владельца на ухудшение цены от закреплённой
отметки плюс комиссию. Проверяются пределы полного резерва и стоимость
частичного исполнения симулятора по его объёму. При значении 0 допустима
нулевая сумма этих компонентов.
Повтор сохраняет первое наблюдение. Исправленную котировку можно проверить
для того же задания. Журнал исполнений, резервы и статус dispatch этой
записью не меняются.

Для чтения нужны права `SELECT` на `paper_accounts` и
`paper_risk_refusals`. Отчёт показывает до 100 последних наблюдений
заданного счёта и задания. Флаг `truncated` означает, что записей больше.
`--as-of` задаёт тот же срез для повторного чтения. Обе команды применения
по-прежнему возвращают ошибку проверки риска. Отсутствующие, просроченные
и невалидные входы обрабатываются их собственными проверками.
[Схема](../../contracts/paper-risk-refusals.schema.json) · [Пример](../../contracts/valid-paper-risk-refusals.json).

## Аналитика портфеля в Telegram

Сначала обновите локальный paper Control. При первом запуске новой версии
он переносит историю ledger в outbox в одной транзакции. На время обновления
завершите запись из предыдущей версии Control и локальных команд paper.
Нужен UUID существующего виртуального счёта. Загрузите токен бота и ID
личного чата через свой локальный скрипт окружения. Для команд также задайте
`TRADINGBOT_TELEGRAM_OWNER_USER_ID` с числовым ID пользователя Telegram.
При другом имени Compose-проекта Control укажите фактическую storage network
в `TRADINGBOT_PAPER_LEDGER_NETWORK`. Для отдельной роли relay укажите её DSN
в `TRADINGBOT_ANALYTICS_LEDGER_DATABASE_URL`.

```powershell
$env:TRADINGBOT_ANALYTICS_ACCOUNT_ID = $paperAccountId
$analyticsCompose = @('-f', 'deploy/notifications/compose.yaml', '-f', 'deploy/notifications/analytics.compose.yaml', '--profile', 'analytics')
docker compose @analyticsCompose up -d --build paper-account-relay portfolio-analytics notifications
```

Команды `/portfolio` и `/positions` показывают состояние счёта.
`/performance` принимает `7d`, `30d` или `all` и заканчивает отчёт
на последнем закрытом дне UTC. По умолчанию берём 30 дней. Бот принимает
команды только от настроенного владельца в личном чате. API доступен
из внутренней сети, данные аналитики хранятся в отдельной PostgreSQL.

### Загрузка рыночных оценок и расходов

Подготовьте JSON-массив событий по схеме ниже для выбранного счёта. Укажите
точный инструмент, версию реестра, цену USD и исходные `observed_at` и
`available_at` из архива. Допустимый возраст цены настраивается через
`TRADINGBOT_ANALYTICS_MARK_MAX_AGE` (по умолчанию `72h`). Для оценки
относительно эталона добавьте точки индекса полной доходности в USD и
задайте его `series_id` в `TRADINGBOT_ANALYTICS_BENCHMARK_ID`.
Полный P&L стратегии появляется после импорта дополнительных расходов и
подтверждения покрытия всех категорий за отчётное окно.
[Схема входа Kafka](../../contracts/paper-valuation-event.schema.json),
[пример одного наблюдения](../../contracts/valid-paper-valuation-event.json).

```powershell
# $valuationArchive — путь к подготовленному JSON-массиву.
$archivePath = (Resolve-Path -LiteralPath $valuationArchive).Path
docker compose @analyticsCompose run --rm --no-deps -v "${archivePath}:/valuations.json:ro" portfolio-analytics -publish-valuation /valuations.json
docker compose @analyticsCompose exec -T portfolio-analytics wget -qO- 'http://127.0.0.1:8080/v1/portfolio?period=30d'
```

Импорт проверяет весь файл до публикации и записывает SHA-256 после Kafka ACK.
При повторе сохраняйте ID наблюдений и исходное содержимое. При нехватке
котировок ответ содержит суммы кэша, количества и время последней оценки.
Стоимость портфеля и зависящие от неё показатели указываются как недоступные.

### Повтор событий счёта

При разрыве проверьте логи `paper-account-relay` и `portfolio-analytics`.
Состояние счёта считается актуальным после подтверждения головы ledger и
получения всех версий до неё. Если Kafka уже удалила нужную историю, повторно
опубликуйте сохранённые события счёта. Для consumer group с истёкшим offset
задайте новый `TRADINGBOT_ANALYTICS_GROUP` и пересоздайте только
`portfolio-analytics`. Если восстанавливается и база аналитики,
повторите импорт архива котировок, эталона и расходов с исходными ID.

```powershell
docker compose @analyticsCompose run --rm --no-deps paper-account-relay -replay-paper-account $paperAccountId
```
